# 백엔드 정리 노트 (refactor/backend-cleanup)

ICCAS 2025 데모용으로 9일 만에 만든 백엔드를, 전면 재작성 없이 **명백한 결함만**
골라 고친 기록이다. 아키텍처(서버가 직접 카메라를 잡고 MJPEG 로 내보내는 구조)와
실측으로 정한 각도 임계값은 그대로 두었다.

작업 브랜치는 `backend/` 디렉터리가 있는 `backend_v2` 에서 땄다. `main` 에는
백엔드가 없다.

커밋은 항목별로 분리했다. 로깅(6번)을 가장 먼저 커밋했는데, `print` -> `logger`
치환이 파일 전체에 걸치기 때문에 뒤이은 동작 변경 커밋의 diff 에 섞이면
무엇이 진짜 수정인지 안 보이기 때문이다.

---

## 1. 스트림 리소스 누수

**문제** 브라우저 탭을 닫아도 서버의 프레임 루프가 계속 돌면서 카메라 핸들과
워커 스레드를 붙잡고 있었다. 다음 사용자가 운동을 시작하면 카메라가 이미
점유되어 있어 더미 스트림으로 떨어졌다.

**원인** `_camera_stream_with_ai` / `_generate_dummy_stream` 의 `while True` 에
종료 조건이 없었다. MJPEG 는 응답이 끝나지 않는 스트림이라, 클라이언트가
사라져도 서버가 알아서 멈추지 않는다.

**수정** 두 루프를 `try/finally` 안으로 넣어 `GeneratorExit` 이 오면 카메라를
해제한다. 엔드포인트는 동기 제너레이터를 `stream_until_disconnect` 로 감싸,
프레임마다 `Request.is_disconnected()` 를 확인하고 `finally` 에서 제너레이터의
`close()` 를 **명시적으로** 호출한다. GC 에 맡기면 정리 시점이 보장되지 않는다.
프레임 생성은 블로킹이라 `run_in_threadpool` 로 넘겨 이벤트 루프를 막지 않는다.

**검증** 서버를 띄우고 `curl -m 4 /video/ai` 로 4초 뒤 강제로 끊었더니 로그에
`클라이언트 연결 종료 감지` -> `종료 요청 수신` -> `더미 비디오 스트림 종료` ->
`스트림 정리 완료` 가 순서대로 찍혔다. 카메라가 없는 개발 머신이라 실제 해제
경로는 가짜 캡처 객체를 물려 별도로 확인했다 (`close()` 후 `release()` 호출됨,
`cap` 이 `None` 이 됨).

**같이 발견한 버그** 프레임 읽기가 3회 연속 실패하면 `return
self._generate_dummy_stream(...)` 로 폴백하게 돼 있었는데, 제너레이터 안의
`return` 은 값을 돌려주는 게 아니라 `StopIteration` 이라 폴백이 실행되지 않고
스트림이 그냥 끊겼다. `yield from` 으로 고쳤다.

## 2. POST 파라미터가 바디로 안 들어감

**문제** 앱이 `/exercise/configure` 에 `{"exercise_type": "..."}` 를 JSON 바디로
보내는데 서버는 그 값을 무시했다. 즉 운동 종류를 아무리 바꿔도 설정은 항상
기본값이었고, configure 는 사실상 아무 일도 하지 않는 엔드포인트였다.

**원인** `exercise_type: str = None`, `kpts: list = None` 처럼 엔드포인트 함수의
평범한 인자로 선언했다. FastAPI 는 `BaseModel` 이 아닌 인자를 **쿼리
파라미터**로 해석하므로 바디는 읽히지 않는다.

**수정** `ExerciseParams(BaseModel)` 을 정의해 바디에서 읽게 했다. 유효성 검사는
`ExerciseAI.validate_exercise_params` 를 `staticmethod` 로 바꾸고 Pydantic
`model_validator` 가 그것을 호출하도록 해, 규칙을 한 군데에만 둔 채 잘못된 입력이
조용히 무시되지 않고 422 로 거절되게 했다. `/exercise/warmup` 도 같은 결함이
있어 함께 고쳤다.

**하위 호환** 앱은 `/exercise/start?exercise_type=...` 를 **쿼리로** 부른다.
바디를 필수로 만들면 앱이 깨지므로, start/warmup 은 바디와 쿼리를 모두 받고
바디를 우선한다 (`_merge_legacy_query`). 프론트엔드는 수정하지 않는다는 전제를
지키기 위한 선택이다.

**검증** 실제 서버에 요청해서 확인했다. `{"exercise_type":"biceps_curl",
"kpts":[5,7,9]}` 를 보내면 프리셋의 `[6,8,10]` 이 `[5,7,9]` 로 덮이고(=바디가
읽힌다), `kpts:[1,2]` / `up_angle:400` / `kpts:[1,2,99]` 는 모두 422 를 받는다.
`/exercise/start?exercise_type=lateral_raise` (바디 없음) 는 그대로 200 이다.

## 3. 정확도 산출의 기본값·하한

**문제** 카메라 앞에 아무도 없어도 화면에 "85%" 가 떴다. 측정에 실패한 상태와
측정해보니 85% 인 상태를 사용자가 구분할 수 없었다. 재활 앱에서 이건 단순한
표시 오류가 아니라 잘못된 피드백이다.

**원인** `calculate_accuracy` 가 검출 실패 시에도, 예외 발생 시에도 `85.0` 을
반환했다. 게다가 하한이 70% 라 30도 넘게 틀어진 자세가 전부 70% 로 뭉개졌다.
시뮬레이션 경로는 사람을 검출하지도 않으면서 `is_detecting = True` 로 켰다.

**수정** 검출 실패와 계산 실패는 `None` 을 반환하고 API 는 `accuracy: null` 로
내린다. `is_detecting` 은 각도를 실제로 뽑아냈을 때만 `True` 다(시뮬레이션
경로는 `False`). 하한 70 은 없애되 **기울기는 그대로 뒀다** — 1도당 1% 감점이라는
매핑은 유지하고 30도에서 잘리던 것만 0% 까지 이어지게 했다. 임계값을 건드리지
말라는 조건 때문에 `up_angle`/`down_angle` 과 30도 스케일은 손대지 않았다.

**검증** 단위 수준으로 확인했다. 목표 각도 정확히 일치 -> 100%, 15도 벗어남 ->
85%, 60도 벗어남 -> **40%** (예전에는 70%), 150도 벗어남 -> 0% 에서 멈춤,
검출 실패 -> `None`. API 응답도 `{"accuracy":null,"is_detecting":false}` 로 나온다.

**처음에 반만 고쳤던 것 (중요)** 위 수정을 끝내고 나서 문서 검증을 돌렸는데,
거기서 이 항목이 절반만 고쳐져 있었다는 게 드러났다. 가짜 기본값 85.0 은
없앴지만 `current_data` 를 갱신하는 코드가 **"사람이 검출된 프레임"** 안에만
있었다. 그래서 한 번 검출된 뒤 사람이 화면 밖으로 나가면 마지막 정확도가
그대로 고정(latch)되어, 아무도 없는데 계속 그 점수가 표시됐다. 검출 실패 시
`None` 을 내려보내기로 한 의미가 실제로는 첫 검출 전까지만 유효했던 셈이다.

가짜 `AIGym` 결과로 "검출됨 -> 사라짐" 시퀀스를 흘려 재현했다. 수정 전에는
사람이 사라져도 `accuracy=100.0 / is_detecting=True` 가 유지됐고, 수정 후에는
`accuracy=None / is_detecting=False` 로 돌아온다. 지금은 정확도와 검출 여부를
**매 프레임** 갱신하고, 추론이 예외를 던진 프레임도 '인식되지 않음'으로 처리한다.
`count` 는 누적 횟수라 일부러 유지한다 — 되돌리면 지금까지 한 운동이 사라진다.

교훈은 "없앤 값" 이 아니라 "그 값을 쓰는 경로 전부"를 확인해야 했다는 것이다.
기본값을 지우는 것과, 상태가 올바른 시점에 갱신되는지는 별개의 문제였다.

**남은 일 (프론트엔드)** `ExerciseDo.tsx` 는 `{exerciseData.accuracy}%` 를 그대로
렌더링하므로 `null` 이면 화면에 `%` 만 남는다. 프론트엔드는 수정 범위 밖이라
건드리지 않았지만, `is_detecting` 을 응답에 추가해 뒀으니 "인식되지 않음" UI 를
붙일 수 있다.

## 4. 전역 단일 인스턴스 → 세션 분리

**문제** `exercise_ai`, `exercise_session` 이 모듈 전역이라 두 사람이 동시에
운동하면 카운트가 섞였다. 두 번째 사람이 start 를 누르면 첫 번째 사람의 카운트가
0으로 리셋됐다.

**원인** 상태를 요청 단위나 사용자 단위가 아니라 프로세스 단위로 들고 있었다.

**수정** `SessionRegistry` 를 만들어 `session_id` 키로 `ExerciseAI` +
`ExerciseSession` 쌍을 격리했다. `POST /sessions`(생성), `GET /sessions`(조회),
`DELETE /sessions/{id}`(삭제) 를 추가하고, 10분간 요청이 없는 세션은 요청 처리
경로에서 정리한다(별도 타이머 스레드를 만들지 않으려고 의도적으로 이렇게 했다).
세션 식별자는 `?session_id=` 또는 `X-Session-Id` 헤더에서 읽고, 둘 다 없으면
`"default"` 로 묶인다 — 기존 앱은 아무것도 보내지 않으므로 지금까지와 똑같이
동작한다.

**솔직한 한계** 카메라는 여전히 서버에 물린 물리 장치 **하나**다. 세션을 나눠도
두 번째 세션의 `VideoCapture` 는 장치 점유 실패로 더미 스트림으로 떨어진다.
즉 이 작업이 고친 것은 **상태 혼선**이지 동시 촬영이 아니다. 진짜 동시 사용은
클라이언트에서 영상을 올려받는 구조여야 가능하고, 그건 이번 범위(아키텍처 재작성
금지) 밖이다. 이 한계는 `SessionRegistry` 독스트링에 그대로 적어 뒀다.

**검증** 세션 두 개를 만들어 각각 `biceps_curl` / `neck_stretch` 로 설정했더니
서로 다른 config 를 유지했고, 한쪽만 start 했을 때 다른 쪽은 400(No active
session) 을 반환했다. 유휴 회수는 타임아웃 1초로 줄여 확인했다.

**작업 중 고친 자기 버그** 처음엔 `get_or_create` 가 touch 보다 회수를 먼저
했다. 그러면 타임아웃 직전에 들어온 요청이 자기 세션을 회수해버리고 빈 상태로
다시 만들어 카운트가 조용히 0이 된다. touch 를 먼저 하도록 순서를 바꿨고,
"같은 객체가 유지되고 count 가 보존되는지" 를 테스트로 확인했다.

## 5. 카메라 백엔드 플랫폼 분기

**문제** Linux/macOS 에서 카메라 초기화가 느리고, 로그에 실패가 잔뜩 찍혀
진짜 카메라 고장처럼 보였다.

**원인** `cv2.CAP_DSHOW`, `cv2.CAP_MSMF` 는 Windows 전용인데 OS 와 무관하게 항상
시도했다. 백엔드 3종 × 인덱스 3종 = 9번을 도는 동안 앞의 6번은 다른 OS 에서
반드시 실패한다.

**수정** `platform.system()` 으로 분기해 Windows 는 DSHOW/MSMF, Linux 는 V4L2,
macOS 는 AVFOUNDATION 만 시도하고, 공통 폴백 `CAP_ANY` 를 항상 마지막에 둔다.
일부 OpenCV 빌드에 상수가 없을 수 있어 `getattr` 로 안전하게 접근한다.
**의도된 3단 폴백(백엔드 실패 → 더미 스트림 → 시뮬레이션 모드)은 그대로 유지했다.**

**검증** `platform.system()` 을 mock 으로 바꿔 각 OS 에서 선택되는 백엔드 목록을
확인했다. Windows `[DSHOW, MSMF, ANY]`, Linux `[V4L2, ANY]`, macOS
`[AVFOUNDATION, ANY]`, 그 외 `[ANY]`. 모든 경우에 `CAP_ANY` 가 마지막에 남는다.

## 6. 로깅

**문제** 모든 출력이 `print` 였다. 레벨도 타임스탬프도 없고, 운영에서 로그를
끄거나 파일로 보낼 방법이 없었다. 이모지가 섞여 grep 도 불편했다.

**원인** 데모 일정상 가장 빠른 방법을 썼다.

**수정** 전부 `logging` 으로 교체했다. 초기화 성공은 INFO, 폴백 발생은 WARNING,
예외는 `logger.error(..., exc_info=True)` 로 스택까지 남긴다. 이모지는 제거했다.
`basicConfig` 를 로컬 모듈 import **위로** 옮겼는데, `exercise_ai` 가 import
시점에 ultralytics 사용 가능 여부를 로그로 남기기 때문이다 — 순서가 반대면 그
한 줄만 포맷 없이 찍힌다.

**검증** `python -c "import main"` 으로 두 줄 모두 타임스탬프+레벨이 붙어
나오는지 확인했고, `grep -rn "print(" *.py` 로 남은 `print` 가 없는지 확인했다
(카메라 데모 스크립트 제외).

## 7. 리소스 정리 방식

**문제** 프로세스가 끝날 때까지 카메라가 잡혀 있는 경우가 있었다.

**원인** `__del__` 소멸자에서 카메라를 해제했다. `__del__` 은 마지막 참조가
사라질 때만 불리는데, 스트림 제너레이터나 예외 트레이스백이 인스턴스를 붙잡고
있으면 그 시점이 언제인지 알 수 없다.

**수정** 명시적 `close()` 로 바꾸고 `__enter__`/`__exit__` 를 붙여 `with` 로도
쓸 수 있게 했다. FastAPI `lifespan` 종료 훅에 `registry.close_all()` 을 연결해,
서버가 내려갈 때 모든 세션의 리소스를 확정적으로 정리한다.

**검증** `TestClient` 로 lifespan 을 실제로 돌려, 서버 실행 중에는 카메라가
잡혀 있고(`released=False`) `with` 블록을 벗어나는 순간 해제되는지
(`released=True`) 확인했다. `__del__` 이 클래스에서 사라진 것도 함께 확인했다.

## 8. 잔가지

**`cv3.py` 삭제** 초기 실험 코드였고, 자체적으로 종료 조건 없는 카메라 루프를
갖고 있었다. `/video` 엔드포인트로만 닿을 수 있었는데 앱에서 부르는 곳이 없어
모듈과 엔드포인트를 함께 제거했다. (앱은 `/video/ai` 만 쓴다.)

**CORS** `allow_origins=["*"]` 와 `allow_credentials=True` 는 같이 쓸 수 없다.
브라우저는 자격증명이 붙은 요청에 대해 `Access-Control-Allow-Origin: *` 를
거부하므로, 이 조합은 "전부 허용"이 아니라 "브라우저에서 전부 실패"가 된다.
이 API 는 쿠키도 Authorization 헤더도 쓰지 않으므로 `allow_credentials=False`
로 끄고 와일드카드 오리진을 유지했다 (앱이 에뮬레이터/실기기 등 여러 오리진에서
접근한다). 프리플라이트 응답에 `allow-credentials` 가 사라진 것으로 확인했다.

**FPS 주석** `time.sleep(0.015)` 에 "30 FPS 제한"이라고 적혀 있었지만 실제로는
약 66 FPS 다. **값이 아니라 주석을 고쳤다.** 실질적인 프레임 상한은 이 sleep 이
아니라 카메라(`CAP_PROP_FPS=30`)와 추론 시간이고, 값을 0.03 으로 올리면 30 FPS
카메라 위에 30 FPS 제한을 한 번 더 걸어 오히려 느려지기 때문이다. 더미 스트림
쪽 `sleep(0.03)` 은 카메라가 없어 그 값이 실제 상한이 맞으므로 그대로 뒀다.
(30 FPS 로 실제 제한하고 싶다면 값을 바꾸는 쪽이 맞다 — 의도만 정해주면 된다.)

**그 외** `json`, `asyncio`, `WebSocket` import 가 처음부터 쓰이지 않아 지웠고,
커밋돼 있던 `backend/__pycache__` 를 추적에서 빼고 `.gitignore` 에 넣었다.

## 손대지 않은 것과 그 이유

**서버가 카메라를 직접 잡는 구조** 이게 이 백엔드의 가장 큰 구조적 제약이다.
서버 웹캠 한 대를 MJPEG 로 내보내므로 원격 사용자는 자기 모습을 볼 수 없고,
동시 사용자도 원리상 불가능하다. 제대로 고치려면 클라이언트에서 프레임을 받아
처리하거나 온디바이스 추론으로 가야 하는데, 그건 아키텍처 재작성이라 이번
범위 밖이다. 데모는 "발표자 노트북 앞에서 시연"이 전제였고 그 전제 안에서는
동작한다.

**각도 임계값과 `predefined_configs`** 실측으로 정한 값이라 그대로 뒀다.
정확도 매핑의 30도 스케일도 같은 이유로 유지했고, 하한 70 만 제거했다.

**MJPEG 스트리밍 방식** WebRTC 가 지연·대역폭 면에서 낫지만 새 라이브러리와
시그널링 서버가 필요하다. 요구 조건(기존 requirements.txt 범위)에 맞지 않아
그대로 뒀다.

**`is_ready()`** `return ULTRALYTICS_AVAILABLE or True` 라 항상 `True` 다.
사실상 의미 없는 함수지만 `/health` 응답 형태를 바꾸면 앱의 연결 체크에 영향이
갈 수 있어, 기존 필드는 그대로 두고 `ultralytics_available` 을 **추가**하는
방식으로 실제 상태를 노출했다.

**`update_exercise_settings()`** 호출하는 곳이 없는 죽은 코드다. 지우는 게
맞지만 `validate_exercise_params` 유지가 요구 사항이었고 이 함수가 그 유일한
호출자라, 이번엔 남겨 뒀다. 다음 정리 때 후보다.

**`manual_camera_check.py`** 독립 카메라 데모라 서버와 무관해 내용은 그대로
뒀다. 다만 원래 이름 `test.py` 가 표준 라이브러리의 `test` 패키지를 가려서
이름만 바꿨다.

## 검증 환경

이 머신에는 **ultralytics 도 카메라도 없다.** 오히려 폴백 경로를 검증하기에
좋은 조건이라, 다음을 확인했다.

- `python -c "import main"` — 항목마다 통과
- ultralytics 없이 uvicorn 기동 성공, `/health` 200
- 카메라 없이 더미 스트림으로 자동 전환, 시뮬레이션 카운트 동작 (6초 스트리밍 후
  `count: 1`)
- 클라이언트 강제 종료 시 정리 로그 4줄 순서대로 확인
- 세션 격리 / 유휴 회수 / 종료 훅 정리 확인

실제 카메라와 ultralytics 가 있는 환경에서의 추론 정확도는 이 머신에서 검증할 수
없었다. 데모 노트북에서 한 번 돌려보는 게 좋다.

### 문서 검증 패스

코드 수정을 끝낸 뒤, `README.md` 와 `TEST_GUIDE.md` 의 모든 사실 주장(포트,
엔드포인트, 파라미터 위치, 응답 필드, 로그 문구, 화면 이름 등)을 추출해 실제
코드와 `TestClient` 실행 결과에 대고 하나씩 대조했다. 122건 중 99건은 사실이었고,
나머지에서 다음이 드러났다.

- **3번 항목이 절반만 고쳐져 있었다** (위 latch 버그). 문서 검증이 코드 버그를
  잡아낸 경우다.
- `uvicorn --log-level debug` 로는 이 앱의 DEBUG 로그를 볼 수 없었다.
  `basicConfig` 가 root 를 INFO 로 고정하고, uvicorn 의 옵션은 `uvicorn.*`
  로거만 바꾸기 때문이다. `LOG_LEVEL` 환경변수를 추가해 문서의 디버깅 안내가
  실제로 동작하게 만들었다.
- 유휴 세션 정리에 백그라운드 타이머가 없다는 사실을 문서가 명시하지 않고
  있었다. 서버가 완전히 유휴면 정리가 영영 일어나지 않는다.
- `configure` 에 쿼리만 보내면 "무시된다"고 적었지만 실제로는 422 로 거절된다.
- 그 밖에 문서가 가리키던 존재하지 않는 화면(`ExerciseTestPage`), 영어인데
  한국어라고 적힌 UI 라벨, 포트를 바꿀 때 고쳐야 할 곳이 두 곳이 아니라 세
  곳이라는 점 등을 정정했다.

문서를 코드에 맞추는 작업이 코드 버그를 하나 찾아냈다는 게 이 패스의 요점이다.
